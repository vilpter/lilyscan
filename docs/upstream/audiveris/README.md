# Contributing bug fixes to Audiveris

A work plan for fixing real Audiveris bugs and sending the fixes upstream as pull requests. It is written to be picked up cold, for example by a separate (cloud) session: everything needed is in this folder or linked from it.

Lilyscan runs Audiveris 5.11.0 as its engine and hit each bug below while being built and evaluated. Lilyscan itself never patches Audiveris (design doc D6) and pins a released version (D7). This work is separate: fix the bugs upstream, then pick the fixes up through a later release.

## Ground rules

- **Ask before posting.** Issues, comments and pull requests on `Audiveris/audiveris` appear under the owner's GitHub account (`vilpter`). Draft each text in `drafts/` next to this file and get the owner's explicit OK in the session before posting it.
- **Public inputs only.** Use the files in `repro/` (generated by Lilyscan; AGPL project content) or public-domain scores (IMSLP). Never use the owner's private photos or scans, and never describe their content. Engrave repro PDFs with `lilypond -dno-point-and-click`: otherwise every note links to the source file by its full local path.
- **One bug per branch and per pull request,** based on upstream `development`, not `master`: all recent community pull requests target `development`, and `master` is the release branch.
- **Match the upstream code.** Audiveris is formatted with the NetBeans formatter: a space before the parameter list in declarations (`isStaffArc (Arc arc)`) but not in calls, braces on their own line for methods and classes, and `//----//` banners above methods. Keep each change as small as the fix allows.
- **Commit messages** follow upstream style: one short imperative sentence, no prefix (for example, "Scale a sheet on its dominant staff size, not its largest"). Put the reasoning in the pull request.
- **No references to Claude, Anthropic or AI assistance** in code, comments, commit messages, pull request or issue text.
- **Licensing:** Audiveris is AGPL-3.0, and contributions are made under that license. There is no CONTRIBUTING file, CLA or AI-contribution policy upstream (checked 2026-09-27); check again before the first pull request.
- **Do not change Lilyscan code** in this work, except for this folder and its `STATUS.md`.

## Setup (Linux)

Audiveris `development` needs **Java 25** (`theMinJavaVersion = 25` in `gradle.properties`); its CI uses Zulu 25 on `ubuntu-latest`.

```bash
java -version    # need 25
# If missing, a JDK 25 tarball (Temurin shown; Zulu is what upstream CI uses):
curl -L -o /tmp/jdk25.tar.gz "https://api.adoptium.net/v3/binary/latest/25/ga/linux/x64/jdk/hotspot/normal/eclipse"
mkdir -p ~/jdk && tar -xzf /tmp/jdk25.tar.gz -C ~/jdk --strip-components=1
export JAVA_HOME=~/jdk PATH=~/jdk/bin:$PATH

git clone https://github.com/vilpter/audiveris.git
cd audiveris
git remote add upstream https://github.com/Audiveris/audiveris.git
git fetch upstream
git switch -c fix/<short-name> upstream/development

./gradlew build -x test    # as upstream CI does
./gradlew test
```

The fork `vilpter/audiveris` exists (created 2026-09-27) and keeps all upstream branches. Before each new branch, sync its `development` with upstream's: `git fetch upstream && git push origin upstream/development:development`.

OCR: most steps run without Tesseract data, but TEXTS comes before CURVES, and OCR results can change what later steps see. To reproduce with OCR as Lilyscan runs it, install English data the way upstream CI does: `.github/install-tessdata.sh eng`, with `TESSDATA_PREFIX` pointing at the install folder.

Run the CLI from source with comma-separated arguments:

```bash
./gradlew run -PcmdLineArgs="-batch,-export,-output,/tmp/out,--,/path/to/input.pdf"
```

The log goes to the console and to `/tmp/out/<book>-<timestamp>.log`. Where Lilyscan's log excerpts below say 5.11.0, compare with a `development` build: a bug may already be fixed there (`development` was 102 commits ahead of 5.11.0 on 2026-09-27).

## Workflow for each bug

1. **Reproduce on `development`** with the input from `repro/`. If it does not reproduce, bisect against the `5.11.0` tag to find the commit that fixed it, record that in `STATUS.md`, and move on.
2. **Find the root cause.** Explain *why* the value is null or the state is inconsistent. Add a null check only where null is a legitimate state (the Javadoc of the method returning it says so). Otherwise fix what produced the bad state.
3. **Search upstream issues and pull requests** for the stack trace's key frames. If the bug is not reported, draft an issue with the upstream template (`.github/ISSUE_TEMPLATE/bug_report.md`): what fails, the input (link to the file in this folder on GitHub), expected behaviour, environment and the trace.
4. **Fix and test** on `fix/<short-name>`. Add a unit test where the code can be exercised without a full book. Otherwise describe the manual check in the pull request: the input, the log before and after, and that `./gradlew test` passes.
5. **Check for side effects.** A crash fix changes which interpretations survive. Run the fixed build on the other files in `repro/` and on a few public scores, and compare exported MusicXML before and after (`git diff --no-index` on the unzipped `.mxl`, or a note count).
6. **Draft the pull request** in `drafts/`: title, "Fixes #N", what was wrong, why, and what changed, with evidence. Upstream #1012 (<https://github.com/Audiveris/audiveris/pull/1012>) is a good model: short, concrete, and says what the change cannot affect.
7. **After the owner's OK,** push the branch to `vilpter/audiveris` and open the pull request against `Audiveris/audiveris:development`.
8. **Record** the state in `STATUS.md` (reproduced, root cause, issue link, branch, PR link, review state).

If this environment cannot push to `vilpter/audiveris` or cannot use `gh`, save the work as patches (`git format-patch upstream/development`) under `patches/<short-name>/` next to this file, commit them to a Lilyscan branch named `upstream/audiveris`, push it, and say so in `STATUS.md`. A session on the owner's machine can then push and open the PR.

## The bugs, in suggested order

### 1. CURVES crashes when an arc starts outside every staff (NullPointerException in `ArcRetriever.isStaffArc`)

- **Status:** not reported upstream; no pull request (searched 2026-09-27). Tracked in Lilyscan as vilpter/lilyscan#38.
- **Input:** `repro/satb-07.pdf`, a one-page SATB score engraved by LilyPond 2.26.0 from generated music (`repro/satb-07.ly` is its source). 5.11.0 fails the whole book and exports nothing. Simulated photos and some simulated scans of the same page crashed the same way; the plain 300 DPI PNG did not.
- **Trace (5.11.0):**
  ```
  WARN Book.java:2044 | Error processing stub java.lang.NullPointerException: Cannot invoke "org.audiveris.omr.sheet.Staff.isTablature()" because "staff" is null
  Caused by: java.lang.NullPointerException: ...
      at org.audiveris.omr.sheet.curve.ArcRetriever.isStaffArc(ArcRetriever.java:286)
      at org.audiveris.omr.sheet.curve.ArcRetriever.determineShape(ArcRetriever.java:193)
      at org.audiveris.omr.sheet.curve.ArcRetriever.scanArc(ArcRetriever.java:424)
      at org.audiveris.omr.sheet.curve.ArcRetriever.scanImage(ArcRetriever.java:459)
      at org.audiveris.omr.sheet.curve.Curves.buildCurves(Curves.java:136)
      at org.audiveris.omr.sheet.curve.CurvesStep.doit(CurvesStep.java:54)
  WARN CLI.java:956 | Exception occurred java.lang.Exception: Error in reaching step PAGE
  ```
  Just before it, CHORDS logs `No containing measure for HeadChordInter#...`, which may be related.
- **Where:** `isStaffArc` takes `sheet.getStaffManager().getClosestStaff(p0)` for the arc's first point and calls `staff.isTablature()`. `StaffManager.getClosestStaff (Point2D, List<Staff>)` is documented to return null when no staff *area* contains the point (`case 0 -> null`). An arc that starts in a margin or a gap between staff areas therefore crashes the step. `ArcRetriever.java` has not changed on `development` since before 5.11.0.
- **Likely fix:** return `false` when `staff == null`, since an arc outside every staff area cannot be part of a staff line. Then check whether the same unchecked `getClosestStaff` pattern occurs elsewhere (`grep -rn "getClosestStaff(" app/src/main/java`), and fix only the call sites that can really get null. Confirm that the slurs on the page are then found (compare exported slurs with `repro/satb-07.ly`).

### 2. Headless Linux: startup crash in the HiDPI probe (`UnsatisfiedLinkError` escapes `getGdkMaxScale`)

- **Status:** not reported upstream; no pull request. Tracked in Lilyscan as vilpter/lilyscan#30. Lilyscan works around it with `-Dsun.java2d.uiScale=1` in its container.
- **Reproduce:** on Linux without `libgtk-3` (a plain `ubuntu:24.04` container, or most cloud sandboxes), run any batch command, for example `./gradlew run -PcmdLineArgs="-batch,-help"`. Audiveris dies at startup, before reading arguments.
- **Where:** `WellKnowns` runs `enableHiDpiScaling()` in a static initializer. On Linux, when neither `sun.java2d.uiScale` nor `GDK_SCALE` is set, it calls `getGdkMaxScale()`, which does `com.sun.jna.Native.register("gtk-3")` inside `try { ... } catch (Exception ex)`. A missing library throws `UnsatisfiedLinkError`, an `Error` rather than an `Exception`, so it escapes both `catch (Exception ...)` blocks and the static initializer fails. Still the same on `development`.
- **Likely fix:** catch `UnsatisfiedLinkError`, or `LinkageError`, which also covers a GTK present with a missing symbol, in `getGdkMaxScale`, and return 0. Consider also skipping the probe when `GraphicsEnvironment.isHeadless()` is true. That changes behaviour on headless desktops too, so propose it only as a second step.
- **Test:** hard to unit-test (static initializer, native library). Show the before/after startup in a container without GTK, and the unchanged scaling on a desktop with GTK if one is available.

### 3. Export produces nothing after a sheet fails to reload (upstream #971)

- **Status:** **already reported upstream** by another user with public reproducers: <https://github.com/Audiveris/audiveris/issues/971> (open, no pull request, 2026-09-27). Lilyscan hit it on 5 of 31 real phone photos (vilpter/lilyscan#48; those photos are private). Our logs show exactly the chain described there.
- **Chain (5.11.0):** after all sheets reach PAGE, `Book.reduceScores` reloads sheets. Unmarshalling one throws `NullPointerException: Cannot read the array length because "this.sequences" is null` in `RunTable.afterMarshal` (called from `RunTable.afterUnmarshal`). The fallback then reopens the book's zip filesystem and throws `FileSystemAlreadyExistsException`. `SheetStub.getSheet()` returns null, and `Score.getPage` (`sheet.getPages()`) throws the NPE seen in `Voices.refineScore`. No MusicXML is exported, and storing the `.omr` fails with `FileSystemAlreadyExistsException` too.
- **Two defects**, as the reporter notes; each can be its own pull request:
  - **(a)** A run table whose `sequences` is null is marshalled or unmarshalled. Find how `RunTable` gets there (an empty table? a table never filled?), and make marshalling handle it, or make sure it never happens.
  - **(b)** The recovery path opens a zip filesystem that is already open. Reuse the open filesystem, or close it first (`Book.openSheetFolder`, `ZipFileSystem.open`, `Book.store`).
- **Also:** `Score.getPage` dereferences a possibly null sheet. Once (a) and (b) are fixed, a missing sheet should give a clear error, not an NPE.
- **Before starting,** read the whole #971 thread for newer comments, and comment there with a plan (after the owner's OK) so no one duplicates the work.

### 4. RHYTHMS crashes on a null measure (NullPointerException in `Voices.refineSystem`)

- **Status:** not reported upstream; no pull request.
- **Input:** `repro/satb-01-scan-prepared.png`, a simulated scan of a generated SATB page after Lilyscan's Stage 1 (4.8 MB). 5.11.0 fails at RHYTHMS and exports nothing.
- **Trace (5.11.0):**
  ```
  WARN Book.java:2044 | Error processing stub java.lang.NullPointerException: Cannot invoke "org.audiveris.omr.sheet.rhythm.Measure.purgeVoices()" because "measure" is null
      at org.audiveris.omr.sheet.rhythm.Voices.refineSystem(Voices.java:430)
      at org.audiveris.omr.sheet.rhythm.PageRhythm.processRanges(PageRhythm.java:288)
      at org.audiveris.omr.sheet.rhythm.PageRhythm.process(PageRhythm.java:248)
      at org.audiveris.omr.sheet.rhythm.RhythmsStep.doit(RhythmsStep.java:192)
  ```
- **Where to start:** `Voices.refineSystem` around line 430: which lookup yields the null measure (a part or staff with no measure in that stack?). `Voices.java` has not changed since 5.11.0 on `development`.
- **Note:** this came from an older Lilyscan Stage 1, so the exact image in `repro/` is the input that crashed. Confirm it still crashes on `development` before digging in.

### 5. A small solo staff above a grand staff: systems split in two (recognition, not a crash): needs a public repro

- **Status:** not reported upstream as far as found. Related open issues: #1011 (sheet scale taken from a minority staff size, fixed by #1012 on `development`), #992 (repeats lost on a smaller staff), #364 (mixed normal and small heads).
- **Seen on:** real phone photos of the piano book of a violin method (private, not shareable). Each system is a violin staff at cue size above the piano's grand staff. 5.11.0 often takes one system for two stacked ones (the violin, then the piano), makes the piano's two staves separate one-staff parts, and misses barlines, so the piano part comes out in pieces.
- **No public repro yet.** `repro/accompaniment.ly` engraves this layout (violin at 2/3 size above a piano). Its clean 300 DPI engraving and a simulated photo of it both read correctly on 5.11.0. Next steps: more systems per page, a real photo or scan of a printout, and public-domain piano parts of violin methods from IMSLP.
- **Why it matters:** every piano part of a method book for violin, cello or flute has this layout.
- **This is the hardest one.** Once reproduced, start from how systems are assembled from staves (`SystemManager`, `GridBuilder`/`BarsRetriever`: bar lines connecting staves, braces and brackets). Check whether #1012 (dominant staff size) changes the result on `development`. It is an algorithmic change, so propose it in an issue with before/after evidence before writing much code.

### 6. Batch export with `-sheets` keeps only the last movement

- **Status:** pull request [#1088](https://github.com/Audiveris/audiveris/pull/1088) opened (owner's OK) from `vilpter/audiveris` branch `fix/sheets-export-names`; it carries the report (`drafts/6-sheets-export-pr.md`). No issue found upstream (#533 is related: movements in batch mode).
- **Input:** `repro/two-movements.pdf`, one page with two movements, engraved by LilyPond 2.26.0 from `repro/two-movements.ly`. `-batch -export` gives `mvt1` and `mvt2`; adding `-sheets 1` gives a single `two-movements.mvtnull.mxl` holding movement 2, and with the opus option the export fails (`ZipException: duplicate entry`). Reproduced on 5.11.0 and on `development` (c5381487d).
- **Cause:** with `-sheets`, `CLI` exports a temporary list of scores, and `Score.getId()` (the rank in `book.getScores()`) is null for them. `Book.getScoreExportPaths`, `Book.export` and `OpusExporter.export` then name every movement `.mvtnull`.
- **Fix:** name a score by its rank among the exported scores, with the `.mvt#` suffix only when several are exported (`Book.getScoreName`, plus one line in `OpusExporter`). Other callers export `book.getScores()`, so their names are unchanged.
- **Checked:** the repro with and without `-sheets` and with opus; a later-page selection; 9 other inputs without `-sheets` give identical files; `./gradlew test` passes (216 tests).
- **Lilyscan works around it** by re-reading a book from a copy without the pages that failed, instead of using `-sheets` (#66).

## Finding more bugs

Open upstream issues with stack traces and public inputs are the best candidates (search `is:issue is:open NullPointerException` or `Exception` in `Audiveris/audiveris`). On 2026-09-27 these included #1044 (`MeasureStack.getStandardChordBelow`, editing), #891 (truncated PNG), #884 (`stems` is null), #696 (STEMS, `Integer.intValue()` on null) and #583. Before taking one: reproduce it on `development`, check that it has no linked pull request or recent "I'm working on it" comment, and prefer bugs that make batch transcription fail over GUI-only ones.
